### Step 1: Make the length header count bytes, not characters

**The problem:** the header comes from `message.length()`, which counts characters. But the stream carries bytes, and your reader reads the header as a byte count. The two match only while every character is plain ASCII (English letters, digits, spaces), one byte each.

```java
// MessageWriter.java:5: the header counts characters
int length = message.length();
// Transporter.java:16: the stream gets bytes
out.write(message.getBytes(StandardCharsets.UTF_8));
// MessageReader.java:14: the reader counts bytes
return new String(message.readNBytes(messageLength), StandardCharsets.UTF_8);
```
[`MessageWriter.java:5`](../../src/main/java/org/moe/transport/MessageWriter.java) · [`Connection.java:16`](../../src/main/java/org/moe/transport/Connection.java) · [`MessageReader.java:14`](../../src/main/java/org/moe/transport/MessageReader.java)

**Why it matters:** with one accented letter, say in a merchant name, the header promises fewer bytes than were sent. The reader stops early and reads the leftover bytes as the next header, so every later message is misread: the failure you described in your 9999 decision. Your tests only use digits, so they can't see it.

**The pattern:** *round trip*: write something, read it back, and expect exactly what you started with. It proves both halves of a format agree.

**New concept: characters vs bytes**
A `String` holds characters; a stream carries bytes. UTF-8, the rule your code uses to turn characters into bytes, needs one byte for an ASCII character and two to four for others.

```java
String price = "5€";                                    // 2 characters
byte[] bytes = price.getBytes(StandardCharsets.UTF_8);  // the bytes that would go on the wire
IO.println(price.length());   // 2 → counts characters
IO.println(bytes.length);     // 4 → "€" takes 3 bytes in UTF-8
```

**Prove it with a test:** frame `"CAFÉ"` and write it with `Transporter.writeToStream` into a `ByteArrayOutputStream`. Read those bytes back with `MessageReader.readMessage` (through a `ByteArrayInputStream`, as in your reader test) and expect `"CAFÉ"`. Today it fails.

**What to do:**
1. Write that test in `MessageWriterTest`. Note what you expect back, then run it: red.
2. Make `frame` count the bytes it will send. Run all tests: green.
3. Your carry-over `> 9999` check goes in `frame` too, and should check that same byte count.

**You're done when:** the round trip passes, the old tests stay green, and you can explain in your own words why `length()` isn't the byte count.

### Step 2: Keep the terminal's connection open until the reply is sent

**The problem:** `listen()` keeps the terminal's connection in a local variable, `client`, and returns only the text. Afterwards nothing holds the connection, so there's nowhere to write a reply. Neither socket is ever closed either.

```java
ServerSocket server = new ServerSocket(5001);
IO.println("waiting...");
Socket client = server.accept();
IO.println("Connected from " + client.getInetAddress());
return MessageReader.readMessage(client.getInputStream());
```
[`Switch.java:11-15`](../../src/main/java/org/moe/switching/Switch.java)

**Why it matters:** your next piece sends the 0110 back on this same connection (one TCP connection carries both directions). And a long-running switch that never closes its sockets runs out of them.

**The pattern:** *open, use, close*, all in one block.

**New concept: `try (...)` sets the lifetime**
Java's try-with-resources (from your Brief 01 notes) closes what you open in the brackets when the block ends. That resource exists only inside the block, so every step that needs it, the reply included, goes inside.

```java
try (FileWriter notes = new FileWriter("notes.txt")) {  // 1. open
    notes.write("first line\n");                         // 2. every step that needs it
    notes.write("second line\n");                        //    happens inside the block
}                                                        // 3. closed here, even after an exception
// notes.write("third");  → won't compile: notes only exists inside the block
```

**Prove it with a test:** a lifetime is hard to see in a unit test, so do a real run: start `Main`, then `SimRunner`. The switch still prints `MTI: 0100`.

**What to do:**
1. In `Switch`, put the `ServerSocket` and the accepted `Socket` each in a `try (...)`. Keep "waiting..." before `accept()`.
2. Move the decode-and-print from `Main` into that block, as Brief 01 planned (step 5: the *switch* decodes). `Main` then just starts the switch.
3. Do the same for `SimRunner`'s socket.

**You're done when:** the run still prints `MTI: 0100`, `Main` no longer mentions `Codec`, and you can say why the reply must be written inside the block.

## How a senior would build this part

A senior would make reading and writing mirror images in `transport`: each takes a stream and alone knows the header rules for its direction. The switch would own a whole terminal conversation, from `accept()` to the reply, and `Main` would only start it. Because that conversation takes plain streams, a test can drive it with in-memory streams, as your reader test does. Your package split stays as it is.

```java
// transport: a mirrored pair
public static String readMessage(InputStream in) throws IOException { ... }                  // MessageReader, as today
public static void writeMessage(OutputStream out, String message) throws IOException { ... }  // MessageWriter: header + bytes in one place

// switching: the switch owns one terminal conversation
public static void serve(int port) throws IOException { ... }                                 // try (...) around the sockets, then handle(...)
public static void handle(InputStream fromTerminal, OutputStream toTerminal) throws IOException { ... } // read, decode, later: reply
```
