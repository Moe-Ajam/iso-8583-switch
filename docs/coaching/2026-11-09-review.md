### Step 1: Return the message instead of printing it

**The problem:** `readMessage` builds a `Message`, prints two values, and returns nothing (`void`). When the method ends, the `Message` is thrown away.

```java
public static void readMessage(String messageString) {
    Message message = new Message();
    message.setMti(messageString.substring(0, 4));
    System.out.println("MIT: " + message.getMti());
```
[`Codec.java:5-9`](../../src/main/java/org/moe/codec/Codec.java)

**Why it matters:** nothing else can use the result. The switch can't route a message it never receives, and a test can't check a value that only appears on the screen.

**The pattern:** this is *compute, then return*: a method works out an answer and hands it back. The caller decides what to do with it (print it, route it, test it).

**New concept: a method that returns instead of prints**
A method with a return type hands its result to whoever called it. Printing only shows text to a human. The program itself can't read what was printed.

```java
// Before: the caller gets nothing back
static void printHours(String time) {          // time looks like "12:30"
    System.out.println(time.substring(0, 2));
}
// After
static String hours(String time) {
    String h = time.substring(0, 2);           // 1. compute the answer
    return h;                                  // 2. hand it back to the caller
}
// 3. the caller decides:  System.out.println(hours("12:30"));  → prints 12
```

**Prove it with a test:** call `readMessage(SAMPLE)` and check that the result's MTI is `"0100"` (step 2 writes this test).

**What to do:**
1. Change `readMessage` so it returns a `Message`, and remove both `println` calls from it.
2. In `Main`, keep the result in a variable and print its MTI and bitmap there.
3. While you're in `Main`: delete `SAMPLE_WITH_HEADER` (it's never used) and fix the `"MIT"` typo when you move the print.

## How a senior would build this part

A senior would make the codec a *pure* method: a string goes in, a `Message` comes out, nothing is printed and nothing else changes. `Main` (later, the switch) decides what to do with it. The `Message` would hold its fields by number, so one method gives you any of the 128 fields instead of one getter per field. Your package layout and your MTI/bitmap offsets are already fine and stay as they are.

```java
public class Codec {
    public static Message readMessage(String raw) { ... }   // string in, message out, no printing
}
public class Message {
    public String mti() { ... }
    public String bitmap() { ... }
    public String field(int number) { ... }   // field(11) → the STAN, backed by a Map<Integer, String>
}
```

You don't need to change `Message` this round. It becomes the next step once the bitmap is decoded.

## A decision to think about

**You decided:** `Message` has one Java field per data element (`de2`, `de11`, `de37`, `de41`).
**My view:** Wrong for now. Which fields a message carries isn't fixed: the bitmap decides, and your sample alone has 17 of them. With one Java field per element, every new element means editing `Message`, and the parser can't loop over "whatever the bitmap says is present".
**Question for you:** why did you pick these four fields, and what would you do when the bitmap says field 43 is present?
